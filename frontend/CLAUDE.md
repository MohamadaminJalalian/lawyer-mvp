# پرامپت برای Claude Code — پیاده‌سازی ماژول احراز هویت، نشست و کنترل دسترسی

## نقش و زمینه کار

تو یک توسعه‌دهنده فرانت‌اند ارشد هستی و باید ماژول **احراز هویت، مدیریت نشست و کنترل دسترسی** یک «سامانه مدیریت پرونده دفتر وکالت» را با **Next.js (App Router) + TypeScript** پیاده‌سازی کنی. این ماژول زیرساخت مشترکی است که سایر بخش‌های سامانه (موکل‌ها، پرونده‌ها) روی آن سوار می‌شوند.

**نکات کلی الزامی (حتماً رعایت شود):**

- خروجی باید **کاملاً ریسپانسیو** باشد (موبایل، تبلت، دسکتاپ) و از یک استایل **مدرن، تمیز و حرفه‌ای** استفاده کند (نه استایل پیش‌فرض و قالبی؛ رنگ‌بندی، فاصله‌گذاری، تایپوگرافی و انیمیشن‌های ظریف مناسب یک نرم‌افزار حقوقی/اداری).
- رابط کاربری **RTL و فارسی** است.
- **امکان خروج از حساب (Logout)** باید کامل و قابل‌اعتماد پیاده‌سازی شود، طوری‌که حتی در صورت خطای شبکه در فراخوانی API خروج، اطلاعات نشست سمت فرانت پاک شده و کاربر به صفحه ورود منتقل شود.

## ۴. صفحه ورود (`/auth/login`)

عناصر فرم:

- نام کاربری (متنی، اجباری، حداقل ۳ کاراکتر، بدون فاصله ابتدا/انتها)
- رمز عبور (Password، اجباری، حداقل ۶ کاراکتر) + دکمه/چک‌باکس «نمایش رمز عبور»
- دکمه «ورود به سامانه»

**قانون امنیتی مهم:** رمز عبور هرگز نباید در URL، پیام خطا، Console یا هر نوع لاگ فرانت‌اند نمایش یا ذخیره شود.

### API ورود

```
POST /auth/login
Content-Type: application/json

Request:
{ "username": "admin", "password": "123456" }

Response:
{
  "accessToken": "jwt-access-token",
  "expiresIn": 3600,
  "user": {
    "id": "user-uuid",
    "fullName": "علی رضایی",
    "username": "admin",
    "role": "ADMIN"
  }
}
```

### رفتار پس از ورود موفق

1. ذخیره نشست (ترجیحاً از طریق Cookie امن HttpOnly که بک‌اند تنظیم می‌کند)
2. دریافت/ذخیره اطلاعات کاربر
3. بررسی پارامتر `redirect` در Query String
4. هدایت به مسیر مقصد یا در غیر این صورت به داشبورد (`/`)

نمونه: `/auth/login?redirect=/cases/case-uuid`

### پیام‌های خطا (دقیقاً همین متن‌ها استفاده شود)

| وضعیت                 | پیام                                                      |
| --------------------- | --------------------------------------------------------- |
| نام کاربری خالی       | «نام کاربری را وارد کنید.»                                |
| رمز عبور خالی         | «رمز عبور را وارد کنید.»                                  |
| نام کاربری/رمز نادرست | «نام کاربری یا رمز عبور صحیح نیست.»                       |
| حساب غیرفعال          | «حساب کاربری شما غیرفعال است. با مدیر سیستم تماس بگیرید.» |
| خطای شبکه             | «ارتباط با سرور برقرار نشد. اتصال اینترنت را بررسی کنید.» |
| خطای سرور (۵۰۰)       | «ورود به سامانه با خطا مواجه شد. لطفاً دوباره تلاش کنید.» |

### حالت‌های UI فرم

- Initial: فرم خالی، دکمه فعال
- Error Validation: پیام خطا زیر فیلد مربوطه
- Submitting: دکمه غیرفعال، متن «در حال ورود...»
- Unauthorized: نمایش پیام + پاک‌شدن رمز عبور
- Network Error: حفظ مقادیر فرم و امکان تلاش مجدد
- Success: هدایت بدون نمایش جزئیات فنی

## ۵. مدیریت نشست، اطلاعات کاربر و خروج

### API اطلاعات کاربر

```
GET /auth/me

Response:
{
  "id": "user-uuid",
  "fullName": "علی رضایی",
  "username": "admin",
  "role": "ADMIN"
}
```

نام و نقش کاربر باید در Header/Sidebar نمایش داده شود، مثلاً:

```
علی رضایی
مدیر دفتر
[خروج از حساب]
```

### روش نگهداری نشست

ترجیحاً **Cookie امن + HttpOnly** (تنظیم توسط بک‌اند). Access Token را در `localStorage` ذخیره نکن؛ در صورت عدم پشتیبانی بک‌اند از Cookie در مرحله اول، به‌عنوان راه‌حل موقت، توکن را در حافظه برنامه (state، نه storage) نگه دار و این محدودیت را به‌صورت کامنت در کد مشخص کن.

### `AuthProvider`

یک Context/Provider مشترک در سطح بالای اپ بساز که وضعیت‌های زیر را مدیریت کند:

- `loading` — در حال بررسی نشست
- `authenticated` — کاربر وارد شده
- `unauthenticated` — کاربر وارد نشده/نشست پایان‌یافته
- `error` — خطا در دریافت اطلاعات نشست

و مقادیر/متدهای زیر را expose کند: `user`, `role`, `isAuthenticated`, `login()`, `logout()`, `hasRole(role)`.

### خروج از حساب

```
POST /auth/logout
```

جریان:

1. کلیک روی «خروج از حساب»
2. نمایش Modal تایید با متن: «آیا از خروج از حساب کاربری مطمئن هستید؟» و دکمه‌های «خروج از حساب» / «انصراف»
3. ارسال `POST /auth/logout`
4. پاک‌سازی اطلاعات کاربر از `AuthProvider`
5. پاک‌سازی Cookie/Token
6. هدایت به `/auth/login`

⚠️ **حتی اگر درخواست خروج با خطای شبکه مواجه شود، نشست فرانت باید پاک شده و کاربر به صفحه ورود منتقل شود** — کاربر هرگز نباید در محیط محافظت‌شده باقی بماند.

### مدیریت متمرکز پاسخ ۴۰۱

تمام درخواست‌های API محافظت‌شده باید پاسخ ۴۰۱ را در یک API Client مشترک مدیریت کنند:

1. دریافت ۴۰۱
2. پاک‌سازی نشست و اطلاعات کاربر
3. نمایش پیام: «نشست شما منقضی شده است. لطفاً دوباره وارد شوید.»
4. هدایت به `/auth/login?redirect=<مسیر-فعلی>`

## ۶. Route Guard، کنترل نقش و صفحه عدم دسترسی

### جریان Guard

- ورود کاربر به مسیر محافظت‌شده → بررسی نشست توسط `AuthProvider`
- نشست معتبر → نمایش صفحه
- نشست نامعتبر/موجود نبودن → هدایت به `/auth/login?redirect=<مسیر-فعلی>` (مسیر فعلی باید حفظ شود تا پس از ورود موفق، کاربر به همان‌جا بازگردد)

### حالت‌های Guard

| وضعیت             | رفتار                                         |
| ----------------- | --------------------------------------------- |
| در حال بررسی نشست | نمایش Loader/Skeleton، بدون نمایش محتوای صفحه |
| نشست معتبر        | نمایش Layout اصلی و صفحه                      |
| نشست نامعتبر      | هدایت به صفحه ورود با `redirect`              |
| خطا در بررسی نشست | پیام مناسب + دکمه تلاش مجدد                   |
| پاسخ ۴۰۱          | پاک‌سازی نشست و هدایت به ورود                 |
| پاسخ ۴۰۳          | نمایش کامپوننت «عدم دسترسی»                   |

### کنترل نقش (Hook مشترک)

```ts
const { user, hasRole } = useAuth();
hasRole("ADMIN");
```

نمونه استفاده (دکمه بایگانی پرونده فقط برای ADMIN):

```tsx
{
  user?.role === "ADMIN" && <ArchiveCaseButton caseId={caseId} />;
}
```

یادآوری: مخفی‌کردن دکمه در فرانت‌اند امنیت واقعی ایجاد نمی‌کند؛ بک‌اند باید نقش را برای عملیات حساس (`POST /cases/:id/archive`) بررسی و در صورت نیاز ۴۰۳ برگرداند.

### صفحه/کامپوننت عدم دسترسی (403)

متن: «شما اجازه دسترسی به این بخش را ندارید.» + دکمه «بازگشت به داشبورد» که کاربر را به `/` هدایت می‌کند.

### مدیریت کدهای وضعیت API

| کد  | معنی                     | رفتار فرانت                   |
| --- | ------------------------ | ----------------------------- |
| 200 | موفق                     | نمایش/پردازش داده             |
| 400 | خطای اعتبارسنجی          | نمایش خطا کنار فیلد           |
| 401 | نشست نامعتبر/پایان‌یافته | پاک‌سازی نشست + هدایت به ورود |
| 403 | عدم دسترسی               | نمایش صفحه عدم دسترسی         |
| 404 | یافت نشدن منبع           | پیام مناسب                    |
| 500 | خطای سرور                | پیام عمومی + دکمه تلاش مجدد   |

## ۸. ساختار پیشنهادی فایل‌ها (سازگار با Next.js App Router)

```
src/
  app/
    (auth)/
      auth/login/page.tsx
    (protected)/
      layout.tsx
      page.tsx
      clients/
      cases/
  features/
    auth/
      api/auth.api.ts
      components/
        LoginForm.tsx
        LogoutButton.tsx
        AccessDenied.tsx
      hooks/useAuth.ts
      types/auth.types.ts
      utils/auth-redirect.ts
      providers/AuthProvider.tsx
  lib/
    api-client.ts
    api-error-handler.ts
  middleware.ts
```

مسئولیت هر فایل:

- `LoginForm.tsx`: فرم ورود، اعتبارسنجی، فراخوانی API و نمایش خطاها
- `AuthProvider.tsx`: نگهداری کاربر، وضعیت نشست، `GET /auth/me`، خروج
- `useAuth.ts`: دسترسی ساده به `user`, `role`, `logout`, `hasRole`
- `auth.api.ts`: تعریف درخواست‌های `login`, `logout`, `me`
- `api-client.ts`: ارسال متمرکز درخواست‌ها + مدیریت خطاهای مشترک (۴۰۱ به‌خصوص)
- `(protected)/layout.tsx`: محافظت از مسیرهای داخلی + نمایش Layout اصلی
- `AccessDenied.tsx`: نمایش پیام ۴۰۳
- `middleware.ts`: کنترل اولیه مسیرها در سطح Next.js (در صورت هماهنگی با نوع نشست/کوکی)

## ۹. محدوده کار (فقط همین‌ها را پیاده‌سازی کن)

- صفحه ورود کامل با اعتبارسنجی و اتصال به API واقعی
- `AuthProvider` + `useAuth` + نمایش نام/نقش در Header/Sidebar
- Route Guard برای تمام مسیرهای محافظت‌شده + حفظ و بازگشت به `redirect`
- خروج از حساب با Modal تایید
- مدیریت متمرکز خطاهای ۴۰۱ و ۴۰۳
- کنترل نمایش عملیات بر اساس نقش (نمونه: دکمه بایگانی پرونده)
- صفحه/کامپوننت عدم دسترسی

## ۱۰. خارج از محدوده (پیاده‌سازی نکن)

ثبت‌نام کاربر جدید، فراموشی/بازیابی رمز، تغییر رمز توسط کاربر، ورود با OTP یا Google، تایید دو مرحله‌ای، مدیریت کاربران/نقش‌های پیچیده، تاریخچه ورود/خروج، محدودیت تلاش‌های ناموفق، Captcha، مدیریت چند دستگاه هم‌زمان، Token Refresh پیچیده، ویرایش پروفایل.

## ۱۱. الزامات نهایی خروجی (Definition of Done)

- کد کامل، قابل اجرا و بدون خطای Build
- تمام Mock دیتا برای تست محلی (در صورت نبود بک‌اند واقعی) شامل حداقل یک کاربر ADMIN و یک کاربر STAFF
- استایل مدرن، ریسپانسیو و RTL
- خروج از حساب همیشه کار می‌کند (حتی در خطای شبکه)
- رمز عبور هیچ‌گاه در URL/لاگ/Storage ناامن ذخیره نمی‌شود
- کامنت‌گذاری مناسب در بخش‌های کلیدی (به‌خصوص تصمیم‌های مربوط به نگهداری نشست)

لطفاً پیش از نوشتن کد، ساختار پروژه پیشنهادی بالا را ایجاد کن و سپس فایل‌ها را به ترتیب زیر بساز: تایپ‌ها → API client → AuthProvider/useAuth → LoginForm → صفحه ورود → Layout محافظت‌شده/Guard → AccessDenied → LogoutButton → اتصال نهایی همه بخش‌ها.
